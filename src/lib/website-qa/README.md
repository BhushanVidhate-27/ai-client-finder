# Website QA / Self-Fix Agent (`website-qa`)

Deterministic QA + safe auto-fix for the websites generated by the website-coding agent.
It audits a project workspace, applies only fixes it can prove from its own findings, rebuilds,
and re-verifies — never inventing a fact.

Registered in `src/lib/agents/registry.ts` as the `website_qa` job agent. It drives the Step 9
agent loop (`runAgentLoop`); the QA engine itself is pure functions with no agent dependency.

## Guarantees

| Guarantee | How it is enforced |
| --- | --- |
| Never invents facts | `QaReferences.verifiedFacts` / `unknowns` are the only source of truth; `targetNiche` is a hint, never evidence. Every fix removes or neutralizes evidence — none adds new claims. |
| Fixes are deterministic | `planFixes` + `applyFixes` reproduce each fix from the issue's `evidence` string alone. Re-running on the same input gives the same output. |
| Read-only unless asked | `website.validate`, `website.qa`, `workspace.list`/`read` are `read`; only `qa.fix` (write) and `website.build` (execute) mutate, and `workspace.delete` is never chosen by logic (exists for manual control only). |
| No external contact | No `fetch`, web browsing, or arbitrary `child_process` — content is judged against supplied evidence only. |
| Completion requires a durable build | The verification gate demands a persisted `build.json` (`status: "success"`), never just a fresh in-memory validation. |
| Isolation preserved | All work stays inside the project's `WORKSPACES_ROOT` directory; traversal out is a critical finding. |

## The QA engine (`rules.ts`)

`runQaAudit({ files, refs, build })` is a pure function. It collects evidence from the lead,
research, contact, and verified facts, then runs 23 checks grouped into four audits:

| Check id | Category | Fails when |
| --- | --- | --- |
| `qa-check-required-files` | structural | a required file is missing |
| `qa-check-no-empty-files` / `qa-check-homepage` | structural | required files are empty, or there is no home page |
| `qa-check-build-validator` | structural | the supplied build findings contain a blocking error |
| `qa-check-links` / nav | structural / responsive | an internal link does not resolve, or navigation is empty |
| `qa-check-no-traversal` / `qa-check-no-unsafe-urls` | structural / link | a link escapes the workspace or is `javascript:` / `//example.com` |
| `qa-check-contacts-verified` | contact | an email/phone shown on the site is not present in verified sources |
| `qa-check-no-unsourced-testimonials` | content | a testimonial quote is not present in verified evidence |
| `qa-check-no-fabricated-reviews` / `-services` / `-years` / `-pricing` / `-awards` | content | counts, service lists, founding years, prices, or awards not backed by evidence |
| `qa-check-responsive-widths` / `qa-check-viewport` | responsive | fixed-width layouts or missing viewport tag (mobile) |
| `qa-check-images-alt`, `qa-check-link-text`, `qa-check-input-labels`, `qa-check-heading-structure`, `qa-check-page-titles` | accessibility | missing alt, empty link labels, unlabeled inputs, multiple `<h1>`, empty titles |
| `qa-check-business-claims` | business-safety | a claim ("we specialize in…", "we offer…", superlatives) has no word-level support in evidence, cites an unverified location, repeats explicitly-unknown terms, or asserts the campaign `targetNiche` without support (critical) |

Severity: `critical` (contact/safety/link violations), `high` (most content fabrications,
missing required files, broken links, missing alt), `medium` (viewport, fixed widths, empty link
text), `low` (advisory recommendations). A site is `PASS` only when no issue at `medium` or
above remains.

## The fix catalog (`fixes.ts`)

Only these deterministic operations exist — anything else is left to a human:

| Kind | Effect |
| --- | --- |
| `remove-sentence` | Removes the claiming sentence inside a text block |
| `remove-element` | Removes the exact `<blockquote>` / element that holds the evidence |
| `remove-contact-item` | Removes a leaf contact item (e.g. a `<li>`) showing an unverified number |
| `remove-service-card` | Removes a signed, non-fabricated service card |
| `remove-testimonial` | Removes the blockquote (testimonial/name) not present in evidence |
| `fix-internal-link` | Rewrites `href="/services"` to the single unique existing page (`/services.html`), or removes the link when no page matches |
| `add-alt` | Adds a neutral `alt="Image"` to images lacking one |
| `add-viewport` | Injects a mobile viewport meta into every page's `<head>` |

Fixes are only planned when the evidence supports them; e.g. a broken link with no target page,
a missing required file, and an empty/unsafe link are reported **high and non-fixable** rather
than fabricated away. `applyFixes` returns `applied`, `failed`, and the changed file contents so
the agent can report exactly what changed.

## Loop behavior (`agent.ts`)

One workflow drives every decision (`decideImpl`):

```
iteration 1: website.qa
  PASS + no persistent build manifest      → website.build (durable manifest required first)
  PASS + manifest exists                   → website.validate (final gate)
  FAIL + fixable issues                    → qa.fix → website.build → website.qa (re-audit)
  FAIL + only non-fixable issues           → website.qa again (safe dead-end until iteration bound)
```

Seven tools: `website.qa`, `qa.fix`, `website.build`, `website.validate`, `workspace.list`,
`workspace.read`, `workspace.delete`. The loop stops safely at `MAX_ITERATIONS_REASON` when only
non-fixable issues remain; a clean site completes in **two steps** (`website.qa` →
`website.validate`).

### Verification gate (`verifyImpl`)

A run is `completed` only when **all** of these hold on the last iteration:

1. The final action was `website.validate` and it succeeded.
2. `readBuildManifest` reports a durable `status: "success"` manifest (never a fresh
   in-memory validation).
3. A fresh QA audit is `PASS` (no medium-or-higher issue).
4. No critical/high contact, business-safety, or link issue exists.
5. All required workspace files are present.
6. Workspace isolation is intact.

Anything else ends the run as `failed` with the verification checks listed in the result, so a
failure tells the caller **why** it failed.

## Known limitations

- **No runtime rendering.** Checks are textual/structural — they cannot detect JS-visible
  layout breakage, cross-browser behavior, or visual regressions.
- **No web browsing or live data.** Content is trusted only when it appears in supplied
  evidence; a genuine fact absent from evidence is treated as unsupported (safe by design).
- **No real accessibility guarantee.** The checks catch missing alt, empty labels, empty titles,
  and multi-`<h1>`/heading gaps, but do not claim full WCAG conformance.
- **Flat HTML assumptions.** Tag capture assumes the generated-site structure (non-nested
  blocks); hand-authored nested markup may not be fully matched.
- **Echo-masked claims.** A fabrication inside a sentence that also repeats the business name or
  another verified token needs the sentence window to isolate it; the engine splits on block and
  sentence boundaries to keep this tight.
